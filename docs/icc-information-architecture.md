## 0. Задача, пользователи, рамки

**Главная задача продукта (одно предложение):** за 15 минут от регистрации до
первого работающего контейнера на своём сервере — и дальше ежедневное управление
серверами, контейнерами и деплоями без SSH.

| Рамка | Значение |
|---|---|
| Primary-задача пользователя | «Подключить сервер → видеть состояние → перезапускать контейнеры → деплоить и смотреть журнал» |
| Аудитория и словарь | solo-dev / малая команда без DevOps; словарь профессиональный (сервер, контейнер, образ, деплой, коммит) — термины не упрощаем |
| Топ-задачи | 1) добавить сервер и довести до ONLINE + ACTIVE-агент; 2) увидеть упавший контейнер и перезапустить; 3) запустить деплой и прочитать журнал; 4) пригласить коллегу; 5) переключить пространство и найти нужный ресурс |
| Платформа | desktop (Tauri), окно от 960×600, мышь+клавиатура; мобильных сценариев нет |
| Локаль | интерфейс RU, слаги URL — EN и стабильные; лейблы не склеиваются из строк (устойчивость к переводу) |
| Ограничения | списки курсорные (20/стр); деплои — лимит без курсора; логи — снимки; один активный деплой на конфиг; троттлинг sshOps 6/мин |
| Точки входа | редирект `/` (последнее пространство), переключатель пространств, прямые ссылки (deep link), ссылка-приглашение `/join/…`, CTA в пустых состояниях |
| Признаки успеха | сервер ONLINE < 5 мин; упавший контейнер и логи видны без SSH; первый деплой < 10 мин |
| Владелец IA | владелец продукта; этот документ — источник решений по навигации и лейблам (см. §12) |

Открытых вопросов, меняющих структуру, нет: ответы дают brief, `mvp-scope.md` и
код. Все спорные места решены дефолтами ниже с обоснованием.

## 1. Контентные объекты и схема организации

### 1.1 Объекты (только существующие в API)

| Объект | Ключевые поля | Состояния | Связи |
|---|---|---|---|
| **Пространство** (workspace) | id, name, role (OWNER/MEMBER) | — | ⊃ серверы, проекты, деплои, приглашения |
| **Приглашение** | email, token (показывается один раз), expiresAt | PENDING → принято/отозвано | принадлежит пространству; принимается на `/join` |
| **Сервер** | name, host, port, sshUsername, authType, hostKeyFingerprint, dockerVersion, lastCheckedAt | PENDING / ONLINE / OFFLINE; агент: NOT_INSTALLED / FAILED / STALE / ACTIVE | ⊂ пространство; ⊃ контейнеры; 1 конфиг деплоя → 1 сервер |
| **Контейнер** | id, name, image, state, status, ports, health, restartCount | state — как отдаёт Docker (running/exited/…), показываем как есть | ⊂ сервер |
| **Проект** | name, repoUrl | — | ⊂ пространство; ⊃ конфиги деплоя |
| **Конфиг деплоя** | name, method=GIT_PULL, ref, dockerfile, containerName, ports, serverId | — | ⊂ проект; ссылается на сервер |
| **Деплой** | status, step, log (хвост), imageTag, commitSha, errorCode, exitCode, durationMs | QUEUED → RUNNING → SUCCESS / FAILED; INTERRUPTED (рестарт панели) | ⊂ конфиг; шаги preflight→source→build→run |
| **Аккаунт** | username, email, тема | — | глобальный, вне пространств |

Дерево владения — база иерархии навигации:

```
Пространство
├── Сервер ──┤ Контейнер (логи — свойство контейнера)
├── Проект ──┤ Конфиг деплоя ──┤ Деплой (журнал — свойство деплоя)
└── Приглашение
```

### 1.2 Схема организации

- **Доминирующая схема — задача пользователя** («что я делаю сейчас»), а не тип
  технологии: Поставка, Инфраструктура. Внутри задач — устойчивая иерархия
  владения (пространство → сервер → контейнер; проект → конфиг → деплой).
- Смешение схем запрещено в одном меню: «Серверы» (объект) не соседствуют с
  «Мониторинг» (активность) в одной недифференцированной куче — у каждой группы
  своя подпись.
- Глубина: broad-and-shallow — сколько сущностей, столько уровней, не больше
  (макс. 3 сегмента после `/w/:wid`).
- Фасеты — только там, где метаданные реально отдаёт API: фильтр деплоев
  `?project=&config=`. Фильтр контейнеров по state — клиентский, появится
  только вместе с осознанной необходимостью (не заявлен).
- Вкладки — только соседние представления одного объекта (сервер: Обзор |
  Контейнеры; деплой: Обзор | Журнал). Не для разных разделов.

## 3. Дерево маршрутов и URL-соглашения

### 3.1 As-is (реализовано)

```
/login  /register
/                         редирект: last workspace → /w/:id, иначе /workspaces
/workspaces               список + создание
/account                  профиль, пароль, тема
/w/:workspaceId           каркас; index — участники и инвайт
/join  /join/:wid/:token  приём приглашения
/kit                      витрина примитивов (DEV)
```

### 3.2 To-be (статусы каждого)

```
/w/:wid → redirect /overview                        реализовано (index=home)
/w/:wid/overview                                    частично → срезы 2–4
/w/:wid/servers                                     реализовано (список карточками: TOFU, 429; поиск: Meilisearch /servers/search)
/w/:wid/servers/:sid                                API есть — срез 2 (детали)
/w/:wid/servers/:sid/containers                     API есть — срез 3
/w/:wid/servers/:sid/containers/:cid                API есть — срез 3
/w/:wid/projects                                    реализовано
/w/:wid/projects/:pid                               реализовано (конфиги, запуск)
/w/:wid/deploys?project=&config=                    реализовано (фильтр в URL)
/w/:wid/deploys/:did                                реализовано (шаги, журнал, перезапуск)
/w/:wid/deploys/:did/logs                           реализовано панелью в детали (polling)

Не создаются до API (будущие адреса, чтобы не менять структуру задним числом):
/w/:wid/members · /w/:wid/settings · …/servers/:sid/images|compose|files|terminal
/w/:wid/{monitoring,backups,databases,secrets,ssl,domains,notifications,audit}
```

### 3.3 URL-соглашения

1. Контекст живёт в URL — каждая страница открывается deep link'ом: пространство,
   сервер, контейнер, проект, деплой. Крошки восстанавливают дерево без истории.
2. Слаги EN, стабильные и читаемые (`servers`, `containers`, `deploys`,
   `overview`); лейблы RU им соответствуют. Переименование слага = только с
   редиректом (устаревшие слаги фиксируются, см. §12).
3. Создание не имеет собственного URL: форма создания — модал на странице списка
   (у создания нет shareable-состояния); редактирование — там же. URL получает
   только то, на что можно дать ссылку.
4. Фильтры и пагинация — в query-строке (`?project=`, `?config=`); состояние
   восстанавливается после refresh и back/forward.
5. Форма URL API (`deployments/:did` — плоский) не диктует URL UI: навигационный
   контекст собирает UI (`/w/:wid/deploys/:did`).
6. Неизвестные пути → редирект на `/` (уже реализовано), включая зарезервированные
   адреса гэп-модулей — они не должны выглядеть как «почти работающие».

## 4. Sidebar и верхняя панель

### 4.1 Sidebar (232px; свёрнутый rail 48px)

```
┌──────────────────┐                ┌────┐
│ BIOS             │  логотип       │ B  │  свёрнуто: rail 48px,
│                  │                │    │  иконки + title/aria-label
│ ОБЗОР            │  группа        │    │
│  ▪ Обзор         │  активный:     │ ▪  │
│ ИНФРАСТРУКТУРА   │  --accent-muted│    │
│  ▪ Серверы       │  + --accent    │ ▪  │
│ ПОСТАВКА         │                │    │
│  ▪ Проекты       │                │ ▪  │
│  ▪ Деплои        │                │ ▪  │
└──────────────────┘                └────┘
   232px                            48px
```

- Только основные разделы; подразделы (контейнеры, журнал, конфиги, образы) —
  локальная навигация внутри страницы.
- Свёртывание: кнопка в topbar и клик по логотипу; состояние в
  `bios.sidebar-collapsed`. В rail у каждой иконки — `title` + `aria-label`
  (иконочная навигация без доступного имени запрещена).
- Активный пункт: ровно один, фон `--accent-muted` + текст `--accent`; точное
  совпадение или префикс раздела (`…/servers/:sid/containers` активирует
  «Серверы»); программно — `aria-current="page"` на ссылке.
- Семантика: `<nav aria-label="Основная навигация">` (есть), список ссылок,
  без hover-only; пункты — ссылки (не кнопки-обманки).
- Аккаунт из sidebar убрать — он дублирует меню пользователя (одно место —
  одно назначение).

### 4.2 Верхняя панель (48px)

```
[☰] [workspace switcher ▾] ─ ─ ─ ─ ─ ─ ─ ─ ─ [⌘K*] [тема] [уведомления*] [user ▾]
 ☰ — свернуть         резерв до API ──┘        * — после появления API; без заглушек
```

- **Переключатель пространства** (реализован): label — имя активного или
  «Выберите пространство»; поповер: список, «Все пространства»; ошибка —
  «Повторить», пусто — только «Все пространства».
  Δ К спецификации: переключение **сохраняет подраздел** (`/w/A/servers` →
  `/w/B/servers`), сущность отбрасывается (id невалиден) → список подраздела;
  недоступный подраздел → `/overview`. Сейчас всегда ведёт на корень.
- **Команда/поиск** — см. §8 (палитра, не поиск в шапке).
- **Уведомления**: место зарезервировано между темой и профилем; до API места
  не рисуем.
- **Профиль**: меню пользователя — Аккаунт, Выйти; настройки пространства тут не
  живут (контекст пространства), тема имеет собственную кнопку.

### 4.3 Breadcrumbs

- Показываются от 3 уровней (`/w/:wid/servers/:sid` и глубже); на списках
  верхнего уровня — нет (там h1 + активный пункт).
- Разметка: `<nav aria-label="Breadcrumb"><ol>`, текущий — `aria-current="page"`,
  последний элемент — не ссылка. Крошки отражают иерархию, не историю кликов.
- Родитель всегда доступен из крошек — «назад» работает и при deep link без
  истории; кнопка «назад» браузера — дополнение, не единственный путь.

### 4.4 Доступность и клавиатура

- Landmarks: `header` (topbar), `nav` (sidebar), `main` (контент) — уже есть;
  добавить skip-ссылку «К содержимому» первым фокусом Shell.
- Фокус-порядок: sidebar → topbar → main; popover-меню закрываются Esc,
  возвращают фокус на кнопку; модалка замыкает фокус.
- Polling-обновления (журнал) не перехватывают фокус; изменения статусов
  объявляются через live-region только для завершения деплоя/операции.

## 5. Ключевые пользовательские потоки

### 1. Первый запуск (нет пространств)

`/login` → `/` → memo пуст → `/workspaces` → EmptyState «Создайте первое
пространство» → создание → `/w/:id/overview` → секция серверов с CTA «Добавить
сервер».
*Где я*: активный пункт «Обзор», h1 = имя пространства. *Что дальше*: CTA.

### 2. Онбординг сервера (TOFU, aha-moment)

Обзор/Серверы → «Добавить сервер» (модал, OWNER) → строка PENDING → деталь →
«Проверить SSH» → `trustRequired` → ConfirmDialog TOFU (отпечаток mono, «Сверьте
с хостом») → «Доверять» → ONLINE + dockerVersion → «Установить агента» (OWNER) →
ACTIVE.
Состояния: MEMBER — форм и кнопок нет, одна info-строка «Добавляет владелец»;
424 — Callout danger с `errorCode`; 429 sshOps — блокировка кнопок с отсчётом.

### 3. Инцидент с контейнером

Обзор (stopped > 0) или Серверы → сервер → Контейнеры → строка `exited` →
деталь: журнал (снимок, «Показаны последние N строк»), stats + `readAt` →
OWNER: «Перезапустить» → ConfirmDialog → PATCH → новый state.
*Где я*: крошки «Пространство / Серверы / web-01 / Контейнеры / db-1» + в шапке
детали хост сервера (deep entry не теряет контекст). MEMBER: кнопки нет.

### 4. Деплой: проект → конфиг → деплой → журнал

Проекты → проект → конфиг → «Запустить деплой» (OWNER) → 202 → деталь (QUEUED →
RUNNING; StepProgress = process-навигация шагов) → вкладка «Журнал» (polling 2с
до `finished`, залипание к низу) → SUCCESS (commit/image mono, durationMs) →
«Запустить снова» | «Открыть проект» | `/w/:id/deploys?project=p`.
FAILED — Callout danger с `errorCode`; 409 при активном — warn-Callout.

### 5. Переключение пространства без потери места

`/w/A/servers/web-01` → switcher → «B» → `/w/B/servers` (сущность отброшена,
подраздел сохранён) → недоступно → `/overview`. Memo `bios.lastWorkspace`
обновляется switcher'ом и используется только для редиректа входа.

## 6. Рекомендации против перегруженной навигации

1. **Группы по задачам, не по технологиям** («Поставка», не «Git, CI, CD»).
2. **Заголовок группы — только при ≥2 доступных пунктах**; никаких секций из
   одного пункта.
3. **Нет disabled-пунктов и «Скоро»**: модуль появляется вместе с API; план
   живёт в этом документе.
4. **Плоско, пока честно плоско**: до 8 пунктов — один список.
5. **Логи, метрики, конфиги, шаги — свойства ресурса**, не пункты меню;
   «Логи» станут разделом только с агрегатором (нет API).
6. **Одна сущность — один дом**: образы/compose — в контексте сервера; деплои
   проекта — фильтр списка деплоев, не второй список.
7. **Глубина ≤3 сегментов** после `/w/:wid`; четвёртый уровень — вкладка.
8. **Крошки от 3 уровней**, у каждой детали — родитель-ссылка; возврат не
   зависит от истории.
9. **Палитра вместо поиска в шапке** (§8); поиск сущностей — только с серверным
   поиском.
10. **Постоянные вещи — в topbar**: тема, профиль; аккаунт из sidebar убран.

## 7. Состояния и восстановление

| Ситуация | Поведение и путь восстановления |
|---|---|
| Пространств нет | `/workspaces`: EmptyState + «Создать»; switcher не рендерится |
| Memo пуст/мёртв (404) | `/` → `/workspaces`; молча, без ошибки |
| Пространство недоступно | «Пространство недоступно» + «Ко всем пространствам» (есть) |
| Нет серверов | Обзор/Серверы: EmptyState «Добавить сервер» (OWNER) / info-строка (MEMBER) |
| Проект без конфигов | EmptyState «Добавить конфигурацию» (OWNER) / «Владелец ещё не настроил» (MEMBER) |
| Деплоев нет | EmptyState «История пуста — запустите деплой из конфига» + ссылка «Проекты» |
| Контейнер исчез (404 в детали) | ErrorState «Контейнер не найден» + «К списку контейнеров» |
| MEMBER на owner-действии | Действие не рендерится; если сценарий целиком owner'ский — одна info-строка; 403 от API — errorText как есть |
| Функция без API | Маршрута нет; прямые заходы на зарезервированные адреса → `/` |
| 429 на действии | Кнопка заблокирована с отсчётом, warn-Callout |
| Панель недоступна | ConnectionBanner (есть), контент не блокируется |

Deep entry (из ссылки/истории) всегда даёт: имя объекта в шапке, родителя в
крошках, «что изменилось» — relative-время последней проверки/замера
(`lastCheckedAt`, `readAt`), кнопку возврата к списку. Секреты не отображаются
никогда (эндпоинтов чтения нет — by design).

## 8. Поиск и discovery

**Решение: команда-палитра (⌘/Ctrl+K), не постоянное поле поиска в шапке.**

- Назначение определено: (1) переход к пространствам; (2) команды — создать
  сервер/проект, запустить деплой из конфига, сменить тему, все пункты sidebar;
  (3) позже — переход к сущностям.
- Область v1: команды + пространства. **Сущности — только после появления
  серверного поиска**: курсорные списки не дают честного клиентского поиска по
  всем серверам; палитра не должна притворяться, что ищет то, что не загружено.
- Алиасы из §9 становятся синонимами палитры (host, машина → Сервер).
- Пустой результат палитры: эхо запроса + подсказка ближайших команд, не пустой
  экран. Ранжирование: точное совпадение имени → префикс → подстрока.
- Поиск не вводится «вместо» навигации: лейблы и группировка — первичны (§6).
- Реализация — после среза серверов; сейчас фиксируется только контракт области.

## 9. Лейблы и алиасы

Правила: существительные — для мест, глаголы — для действий; соседние лейблы
различимы и одного уровня; без «Ресурсы», «Инструменты», «Ещё».

| Лейбл (UI) | Что обещает | Алиасы (для палитры/поиска) |
|---|---|---|
| Обзор | Сводка пространства | дашборд, dashboard |
| Серверы | Список хостов | машина, хост, сервер, host |
| Контейнеры | Контейнеры сервера | докер, docker |
| Проекты | Проекты пространства | репозиторий, repo, project |
| Деплои | История запусков деплоя | выкатка, релиз, deployment, deploy |
| Журнал | Хвост вывода деплоя | лог, log, вывод |
| Участники | Люди в пространстве + инвайт | доступ, members |
| Аккаунт | Мой профиль и пароль | профиль, account |
| Пространство | Рабочая область | workspace, воркспейс |

Действия (глаголы): «Добавить сервер», «Проверить SSH», «Установить агента»,
«Перезапустить», «Запустить деплой», «Запустить снова», «Пригласить».
Устаревших лейблов пока нет; при переименовании — старый лейбл и слаг попадают
в эту таблицу как deprecated (см. §12).

## 10. Валидация по сценариям (обязательная проверка IA)

1. **Known-item** — «найти контейнер db-1 и перезапустить».
   Путь: switcher → Серверы → web-01 → Контейнеры → db-1. 5 кликов без поиска;
   при знании ссылки — 1 deep link. Лейблы предсказуемы, активные состояния
   ведут. ✓
2. **Exploratory** — «новый участник осматривает пространство».
   `/w/:id/overview`: метрики → серверы → деплои; из деплоя — «Открыть проект»;
   из сервера — контейнеры. Мир обозрим без обучения: 4 пункта меню, каждая
   страница отвечает «где я / что здесь / куда дальше». ✓
3. **Recovery** — «перешёл по ссылке на удалённый деплой» / «попал в чужое
   пространство».
   Деталь: ErrorState 404 + «К списку деплоев» (ссылка, не тупик); чужое
   пространство: «Пространство недоступно» + «Ко всем пространствам»; неверный
   зарезервированный гэп-URL → `/`. Ни один путь не заканчивается пустым
   экраном. ✓

Сценарии покрывают все три обязательных класса задач из чек-листа скилла.

## 11. Доступность и фронтенд-поведение

- Состояние в URL: пространство/сущность — путь, фильтры — query; refresh,
  back/forward и shared link восстанавливают место и фильтры.
- Разметка: `nav`/`header`/`main` с подписями; крошки — `ol`+`aria-current`;
  меню — `role="menu"` + клавиатура (Esc возвращает фокус); модалки замыкают
  фокус; иконочные кнопки — `aria-label`.
- Loading/empty/error — у каждого списка и секции (см. §7); refetch не
  опустошает контент (react-query кэш, stale-while-revalidate).
- Производительность: курсорные списки — «Ещё»; журнал — ограниченный хвост
  (виртуализация не нужна при бюджете байт); навигация не рендерит гигантских
  деревьев (sidebar статичен).
- Аналитика: инфраструктуры нет — события (nav-click, no-results, 429-hit)
  определяются как контракт на будущее, не внедряются сейчас.

## 12. Ведение (governance)

- Владелец лейблов, алиасов и структуры — владелец продукта; изменения идут
  через этот документ.
- Новый модуль проходит по чек-листу: есть API → назначается группа, лейбл,
  слаг, состояние пустоты; нет API → строка в §2 со статусом, маршрут не
  создаётся.
- Переименование лейбла/слага: старый вариант фиксируется как deprecated
  (таблица §9), для слага — редирект; «мёртвых» адресов не остаётся.
- Пересмотр группировки — при переходе к ≥8 пунктам (включение оверлайнов, §2).

- Не создаёт маршруты, страницы, пункты меню — только спецификация; реализация

  в §2; в UI они не появятся раньше API.

- Не проектирует поиск/фасеты сверх данных, которые реально отдаёт API.
